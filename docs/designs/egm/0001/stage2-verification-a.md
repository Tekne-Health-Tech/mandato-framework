# Stage 2 — Adversarial verification (A): security, data model, extension contracts

Verifier: fresh-context subagent acting as adversarial verifier. Inputs: `AGENTS.md`, `scripts/check-boundaries.sh`, `docs/designs/0001-core-contracts.md` (commit `328d1e0`), `stage0-scope-and-method.md`, and the three stage 1 reports `stage1-goldfish-security-privacy.md` (SEC-*), `stage1-goldfish-data-model.md` (DB-*), `stage1-goldfish-extension-contracts.md` (EXT-*). No design file was modified.

## Method

For every finding I (1) re-read the quoted design text against the design file, line by line, and treated any misreading as grounds for rejection; (2) checked each technical claim against what I know of PostgreSQL 15/17/18, Supabase (PostgREST Data API, `auth.*`, default grants, linter), Expo/Metro, Next.js and the LGPD (Lei 13.709/2018), and marked claims that only hold under an assumption the design does not make; (3) checked whether the gap is **design-level**, meaning it crosses lanes and so belongs in the E0.0 freeze, or whether one lane can decide it locally. Lane-local gaps are capped at **minor**. Severity rubric from stage 0: **blocker** = the contract cannot be frozen as written; **major** = lanes will diverge or rework is likely; **minor** = clarify before or during the freeze; **nit**. Verdicts: **CONFIRMED** (true, and it matters at the stated or adjusted severity), **PLAUSIBLE** (likely true, but it depends on an unstated assumption or part of it is overstated), **REJECTED** (wrong, or not a design-level issue). Duplicates are grouped into clusters K1–K13, listed at the end.

## Notes on downgraded and PLAUSIBLE items

- **SEC-1 (PLAUSIBLE, blocker kept).** The failure scenarios assume the Data API (PostgREST/pg_graphql) can reach `core` or `mod_*`. Supabase exposes only `public` and `graphql_public` by default, and custom schemas get no default grants to `anon`/`authenticated`, so the scenarios fail under defaults. The finding still stands as a blocker for three reasons. (a) §6 Q1 itself talks about "friction with Supabase's API exposure", so the author is considering exposing `mod_*`. (b) If the Next.js handlers call PostgREST with the user's JWT (the common supabase-js pattern), the schemas must be exposed, and then any holder of the anon key and a JWT can bypass `/api/v1`. (c) Whether `has_role` checks `auth.jwt()->>'aal'` (a real Supabase claim; Supabase documents exactly this restrictive-policy pattern) depends on that answer, and `has_role` is frozen in §3.3. One sentence ("the Data API exposes X; everything else is reachable only through `/api/v1` and workers") clears it.
- **SEC-2 (CONFIRMED, one sub-claim overstated).** Item 3, "nothing prevents a module from calling `provider.generate` directly", treats closed modules as adversaries. They are first-party code, and in Python an import-lint is advisory at best. The guard protects against mistakes. Items 1, 2 and 4 hold.
- **SEC-4 → minor.** `EXECUTE` is granted to `PUBLIC` by default on new functions (true), and owners are not bound by `REVOKE` (true). But "no actor parameter, revoke execute, `BEFORE UPDATE/DELETE/TRUNCATE` trigger, non-login owner, optional hash chain" are all choices one lane can make inside the DB lane. The forgery-over-RPC path needs `core` exposed (K1). C3 read-auditing is a new product requirement, not a contract gap. The cross-lane part (who sets the actor for workers) is DB-6 and stays major.
- **SEC-5 (note).** The proposed AAD `table|column|row_id` conflicts with §3.3 "UUIDv7 generated in the database": the app would have to generate the id before encrypting, or drop the row id from AAD. The freeze has to resolve this, which reinforces that the ciphertext format is contract-level.
- **SEC-6 (PLAUSIBLE).** The design never says `audit_event.actor_id` is an FK, so the delete-or-cascade dilemma is hypothetical. LGPD does not demand erasure of accountability records: art. 16 I allows retention to meet a legal or regulatory obligation, and art. 37 requires records of processing. Art. 18 rights also have conditions, for example deletion under VI covers data processed on consent. What does belong in the freeze is a per-module DSR export/erase hook in the manifest and a "no content" rule for `ai_provenance`, because both bind closed modules. Retention periods can be set later.
- **SEC-7 (PLAUSIBLE).** The recursion happens only if `role_assignment`'s own policy calls an invoker `has_role`. A policy like `user_id = auth.uid()` on `role_assignment` makes an invoker `has_role` work for self-checks, so "reads nothing" is wrong. The concern that matters is that closed-module migrations never run in public CI, so a "no `operador` on C3" check has to ship as a conformance check that the closed repos run (ties to K13).
- **SEC-8 → minor.** The scenario says "the design promised anonymity it could not deliver", but the design makes no anonymity promise. Denúncia is listed only as a public-write example, and its module is out of scope (§5). Truncated or HMAC'd rate-limit keys and a TTL on idempotency records are an API-lane implementation choice. If the product wants anonymous denúncias, that requirement belongs to the closed module's design.
- **DB-2 → major.** Technically correct (PG15+ `security_invoker`; views otherwise run with the owner's rights, and the owner bypasses RLS without `FORCE`). The fix is one normative sentence plus a CI check, with no design alternative, so a freeze can go ahead once the sentence is added. The impact if it is missed is still high.
- **DB-5 (PLAUSIBLE).** See SEC-7 on recursion. Wrapping in `(select core.has_role('x'))` and the `(user_id, role)` index are performance work for the DB lane. The `aal2` part duplicates SEC-1.
- **DB-8 (overstated sub-point).** An `operador` reading an `enc_` column in a C1 table gets ciphertext only. The leak needs the application to decrypt on their behalf. The CI gap (`enc_` not checked against the table class) is real.
- **DB-9 (PLAUSIBLE).** Native `uuidv7()` is PostgreSQL 18, so the claim is right that PG 15/17 lack it. I could not verify which PG versions Supabase offers in late 2026 or whether `pg_uuidv7` is available. Either way the implementation sits behind `core.uuid7()` and belongs to the lane. The design text "ordering by id approximates creation time" should not become a sort contract.
- **DB-12 → nit.** `check (id)` on a boolean PK, or an equivalent, is a local DB detail. §2 already makes `tenant.yaml` the identity source.
- **EXT-2 → major.** The claim that `registerModule` "is never defined" misreads §3.1, which maps it to the manifest explicitly. The remaining gaps are real and cross lanes: the exports of referenced files, the missing manifest keys for `PublishTarget`/`ContentEnricher`/`Connector`/`AiProvider`, and the snake/camel spelling. Their blocker-weight core (how module code enters a build) is EXT-1.
- **EXT-4 (note).** The guard and provider signatures differ on purpose: the guard wraps the provider. That is not a defect, only an omission of the wrapping statement. The blocker rests on the undefined "local" and the missing routing hook, which §2 ("the hook is added here first") requires to exist before closed modules can route.
- **EXT-5 (PLAUSIBLE).** The prompt-leak path through task strings is speculative. The `TaskId` grammar is worth one line.
- **EXT-6 → minor.** At 0.x every minor is breaking by definition, and the closed modules release after the E0 lanes. Only two fields need to be in the freeze, because adding them later is itself breaking: `module.schema.json` `schema_version` and a job-envelope `v`. The deprecation window and conformance kit can follow.
- **EXT-1 (overstated sub-point).** Expo can replace JS at runtime through EAS Update, but it replaces whole bundles built in CI, so the per-module conclusion stands. The AGPL questions are for legal and should be recorded as an ADR reference. They do not block freezing the composition mechanism itself.
